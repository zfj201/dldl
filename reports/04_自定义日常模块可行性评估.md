# 香香小助手自定义日常模块可行性评估

> 阶段更新：已恢复可读 Lua 并完成签到离线原型，详见 [06 资源解密记录](06_资源解密与业务恢复.md) 与 [07 模块实现记录](07_模块定位与签到原型.md)。下文保留该阶段的判断／计划，不代表最新完成状态。

日期：2026-10-10。目标：在游戏内置的香香小助手中新增每日签到、乾坤问情谷扫荡、镜之屋每日召唤、众神殿自动膜拜。用户已确认不是独立辅助 App。

## 结论

从功能形态看，这些任务适合做成自动化模块，值得继续验证。但目前不能宣称已经获得四项功能的代码或能够直接接入香香小助手。是否能“加进小助手”，取决于其客户端任务配置、注册、调度，以及服务器对现有单项操作的支持方式。

本轮是评估，没有执行领取、扫荡、召唤或膜拜操作，也没有安装／修改小助手。

“拿到业务逻辑”和“实现自动化”不是同一进度指标。实现已有日常操作往往只需要对应的客户端操作入口、状态与回执，不需要恢复整个游戏，更不需要还原服务器实现。

## 实际恢复量

| 内容 | 已确认状态 | 能否支撑本次功能 |
|---|---|---|
| Java / Android 层 | 6,898 个 Java 导出文件；26 个 JADX 错误 | 有 SDK、生命周期、JNI 桥接信息，尚无这四项玩法的可用调用链 |
| 两个 native 模块 | 8 个运行时分段，共约 20.34 MiB | 用于继续反汇编与定位解密，不等同完整业务源码 |
| Lua 业务脚本 | 已定位解密链，尚无经过验证的这四项业务明文 | 四项完整业务调用链当前验证完成数为 0/4 |
| 明文资源索引 | 13,071 条，主要是图片／音频映射 | 可提供搜索词，不能当作业务模块 |
| 直接 XXTEA 试解 | 8 个文件、5 个观察到的候选字段，无成功长度校验 | 需处理 FairGuard 前置层或在处理后采集 |
| 香香小助手任务系统 | 已确认是游戏内置功能；任务注册和调度实现尚未恢复 | 不能认定有现成插件 API |

无法给出可信的“业务逻辑已解密百分比”：既没有完整模块总表，也没有恢复出目标脚本。0/4 是本次目标功能的验证状态，不代表客户端永远无法恢复。

潜在获取范围：若能在解密／Lua 装载边界采集，可获得被执行路径实际加载的脚本或字节码；覆盖取决于触发了哪些界面、热更新版本和脚本格式。一次运行不会自动覆盖所有功能，部分客户端脚本也只是向服务器发请求。

候选项保存在 `evidence/automation_resource_candidates.json`。其中是图片／音效名称线索，不是实际函数名。

## 四项模块的评估

以下为流程复杂度预估，尚未逐项进行游戏界面和调用验证。

| 模块 | 原理上的适配性 | 需要恢复／观察的最小信息 | 关键边界 |
|---|---|---|---|
| 每日签到 | 高，通常是状态查询与一次领取 | 本日是否已签、是否可领、领取入口、成功回执 | 月签／活动签／累计奖励可能是不同系统；不把补签当免费签到 |
| 乾坤问情谷扫荡 | 适合模块化，具体规则待验证 | 玩法解锁、可扫荡条件、实际目标／层数参数、剩余次数与消耗、结果回执 | 以该玩法真实规则为准，不套用其他副本的体力／关卡模型；不默认购买次数 |
| 镜之屋每日召唤 | 高，若有独立免费次数状态 | 正确召唤池、免费次数或冷却、入口、消耗类型、回执 | 明确每日免费召唤与消耗券／钻石的召唤；不能仅按按钮位置操作 |
| 众神殿自动膜拜 | 高，若客户端可正常手动完成 | 功能解锁、膜拜资格、剩余次数、目标选择、入口与回执 | 核对普通／高级或免费／付费膜拜差异，已完成则跳过 |

以上“高”指任务适合自动化的形态，并非已验证香香小助手兼容性或成功率。

## 内置香香小助手的接入条件

首先查看其任务列表来自哪里：客户端 Lua 表、客户端代码注册、远端配置，还是服务器统一任务。

- 如果任务注册和调度在 Lua 客户端，可考虑增加本地任务项，并复用已有玩法 controller 的正常操作入口。需要处理设置开关、状态、异步回执和顺序执行。
- 如果列表由服务器下发但具体操作可逐项从客户端执行，可以评估在客户端增加独立调度层；仅增加一个 UI 条目并不会自动获得服务器支持。
- 如果小助手只提交固定的一键任务编号，由服务器统一执行，不能假设发送一个新增编号就会产生新功能。需要确认是否能调用已有的单项操作，或改用外部界面自动化。
- 若涉及客户端改包或内存扩展，还需解决加载、版本变化、签名／完整性兼容，不能把本轮分析 dump 直接当作可部署模块。

如果内置助手无法扩展，外部界面自动化可以作为替代方案，但这不等同于已经把模块加入游戏内助手。本目标优先验证内置任务注册与调度，不先转向制作独立辅助 App。

## 建议模块约定（设计，不是已发现的 API）

每个模块应包含：读取当前资格／次数、执行一次正常操作、等待回执、确认完成、跳过原因、失败原因。共享一个串行调度器，避免两个任务同时切换界面或写入游戏状态。

建议状态流程：

```text
检查登录和功能解锁
  -> 检查今日资格／剩余免费次数
  -> 已完成则跳过
  -> 执行一次操作
  -> 等待结果
  -> 回查真实状态
  -> 完成／等待／失败
```

次数与消费规则作为模块参数：签到只领可领奖励；每日召唤默认只用免费次数；膜拜只执行配置允许的档位；乾坤问情谷扫荡按实际可用次数与配置上限执行。超时不等于失败，先回查状态再决定是否重试，避免重复消费。

完成状态以游戏状态／服务端回执为准，本地日期标记只能辅助。跨服、切换角色、游戏每日重置时间都应纳入状态键。

## 最短验证路径

1. 定位内置香香小助手的 Lua 页面、任务列表／注册表、配置来源和执行队列，核实哪些控制逻辑位于客户端。
2. 以“每日签到”为最小样例，观察界面状态，采集它和小助手实际加载的脚本，定位可领判断、调用入口和成功回执。
3. 先证明一个新增模块能显示、执行、确认完成，重复运行会跳过；再推广到召唤、膜拜。
4. 实现乾坤问情谷扫荡，先核实该玩法的可扫荡条件、真实参数与消耗模型，再增加次数上限和结果核对。

此路径将逆向范围收敛到“小助手调度 + 四个玩法 controller + 状态／协议绑定”。当前没有证据需要先完整破解所有资源或恢复全部战斗系统。
