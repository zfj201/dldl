# 香香小助手扩展：真实调用链与签到原型

> 2026-10-11 目标修正：每日签到实际为“斗罗集市→每日礼包”和“学院活动→每日特惠”免费领取。旧修炼补给原型不满足此需求；两项新目标已定位，详见 [最新定位报告](08_每日礼包与每日特惠定位.md)。

日期：2026-10-10。用户指定“扫荡”为 **乾坤问情谷**，助手为 **游戏内置香香小助手**。

## 当前结论

四个目标的客户端入口都已定位，具备制作客户端自定义任务的代码基础。**每日签到已有可回滚 Lua 原型，通过 APK 版及手机热更新版各 15 项离线测试；尚未加载到手机，不能称为实机可用。** 其他三项完成了入口和协议定位，尚未接入执行器。

## 助手不是任意插件协议

真实链路：

```text
SimplifyData.data_list + OneKeyBurdenConst.SimplifyTypeList
    → OneKeyBurdenMainWindow:initOperateList / saveOperateRequest
    → 31601 保存服务器认识的任务设置
    → OneKeyBurdenAutoWindow:requestTask
    → 31602(type, pos)
    → 成功回执 UPDATE_EXECUTE_OPERATE_EVENT
    → updateDataList 前进一项；31603 单独更新奖励
```

原生任务由客户端排序，具体操作交给服务器。`31602` 的 type/pos 为 uint8，服务器不会因为客户端加了编号就获得新实现。

因此新增任务使用本地分支，调用目标玩法的原有 controller；自定义编号必须在 `31601` 保存、`31602` 执行两处隔离。完成条件来自该玩法自己的成功事件／状态核实，不能伪造服务器“执行成功”。

源码证据：`game/onekeyburden/onekeyburden_controller.luac`、`view/onekeyburden_main_window.luac``view/onekeyburden_auto_window.luac`、`sys/net/proto_mate.luac`。APK 和热更新两版均已恢复。

### 两个易混淆点已经排除

- 小助手已有 `type=1,pos=5` “自动领取修炼补给”。客户端配置证明原有此选项；服务器实际覆盖哪些签到奖励仍需实测，自定义普通签到不等于新增服务端能力。
- 小助手已有 `type=10,pos=22` “普通膜拜”，调用体系属于 **GodPalace 神殿**。用户所说 **众神殿是 Pantheon**，不能直接用前者冒充完成目标。

### 乾坤问情谷的证据闭环

热更新 `config/source_data.luac` 的 519 项：`name="乾坤问情谷"`、`extend={3001}`。`sys/jump_const.luac` 中 `Resource=3001`。`DungeonstoneController:registerEvents` 注册此入口；开放键 `resource_dungeon_open`。

扫荡 UI 使用已通关 `config.id`，复用 `send13032(id,num)`。`13030` 返回分类次数列表（`type/day_free_num/day_buy_num`）、通关列表和奖励列表。配置当前每天免费 2 次；执行时应读配置并扣除 `day_free_num`，不可把包含扫荡券的 `cur_free_count` 全当免费。`13032` 回执含 `code/id`，controller 当前空处理；接入时要捕获成功并重新查询 `13030` 验证次数变化。副本类型可能有多个，不能任意硬编码一个关卡。

### 众神殿证据闭环

热更新 `city_data` 22 项名称“众神殿”，开放键 `pantheon_open`；`pantheon_data` 包含众神殿规则。`PantheonTopWindow` 点击膜拜在 `worship_status==TRUE` 时发送 `13251`，无对象参数或付费档位。`13250` 含 `buff_id/reward_lev/red_status/worship_status`，`13251` 含 `code/buff_id`。这一点与 GodPalace 的 `13209(type)` 明确不同。

## 已实现的签到原型

- `modules/daily_sign.lua`：查询→领取→成功或超时核实的状态机。
- `modules/xiangxiang_sign_extension.lua`：小助手注册、保存过滤、执行分流、原事件订阅、定时核实、关闭清理与卸载。
- 自定义标识 `pos=-14101` 仅存在本地；默认关闭，显示“自定义：每日签到”。
- 首次运行先查询，只有状态 0 才领取一次；状态 1/2 跳过，其他状态不擅自补领。
- 成功事件必须匹配日期和更新后的模型状态。请求 10 秒超时后再查一次；状态无法确认则停止队列，当前会话禁止对同账号同周期自动重发。
- 切换角色／取消时清理回调和定时器；提交后的不确定记录保留在当前扩展实例内。
- 原生回执需匹配当前 type/pos，避免迟到回执推进自定义任务。
- 卸载会恢复方法与注册项；要求先关闭小助手窗口。尚不支持跨重启保存自定义设置，卸载／重启也不保留不确定记录。

原型本身不包含 APK 加载器或 Frida 注入器。在游戏 Lua 环境里，需先加载原小助手类，再加载这两份模块，在打开小助手窗口前调用 `install`。这只是约定，**实际加载入口尚未验证**，不能直接把文件复制到手机就当作可用。

## 验证

```sh
PYTHONPATH=.tools python3 tests/test_daily_sign.py
PYTHONPATH=.tools python3 tests/test_daily_sign.py --hotupdate
```

测试使用 Lua 5.1，实际加载恢复的原游戏控制器、模型和队列方法；Cocos UI、网络、计时与事件环境由本地测试替身提供。网络发送仅捕获到内存，不访问游戏服务器。

两种代码版本各 15 项通过：领取成功、重复启动、重复通知、已签跳过、额外领取跳过、超时查状态、未知结果不重发、角色变化、取消、跨日、字段缺失、自定义编号过滤、原任务衔接、失败回执不误判、卸载恢复等场景。明细：`evidence/phase2_sign_tests_apk.json`、`phase2_sign_tests_hotupdate.json`。

这验证了 Lua 逻辑和已模拟条件下的接入关系，没有验证 Cocos 界面、网络时序、真实奖励弹窗、重登／热更新后的加载效果。
