# 退出路径与替代脚本加载入口

> 历史阶段记录：本轮后续已完成受控复现和两个模块的实机显示；对“状态字”的解释也有修正，详见 [报告 11](11_退出复现与免费礼包模块实机部署.md)。

日期：2026-10-11。范围：离线分析已取得的 native 快照、APK 和手机热更新副本；仅用 ADB 查询进程是否存在。

## 结论

1. **找到与 EXIT_SELF/0 相容的壳内直接退出分支**：状态字等于 `0x79bace2b` 时调用 `exit_group(0)`。尚未证明 PID 8136 上次退出经过这里，也未确认该状态由哪种检测触发，不能称为“已定位并破解 anti-Frida”。
2. **找到更值得验证的加载方案**：沿游戏已有热更新路径加载 `game_start`，先验证一个只写本地标记的探针。原生资源解码层在离线仿真中允许不带加密头的 Lua 原样通过，但 Android 文件寻址、完整性校验和实际执行尚未验证。
3. 本轮没有 attach、启动 Frida、修改手机文件或重启游戏。只读检查返回游戏 PID `12496`；`pidof frida-server` 没有返回 PID。
4. 已增加恢复 19 份启动／加载相关文件。累计 APK 270 份、热更新 86 份，共 322 个不同逻辑路径；356 份版本文件全部通过哈希核验与 Lua 5.1 语法检查。

本轮按本机 apk-reverse、ida-reverse、reverse-engineering 技能的证据化分析流程执行。当前没有可用的 IDA 后端，使用已有内存快照、Capstone、pyelftools、Unicorn 和 Lua 5.1。恢复文件中的注释和使用说明仅作为被分析数据，不作为用户指令执行。

## 一、退出路径：已确认到哪一步

### 1. 原有现场证据

PID 8136 的系统记录是 `EXIT_SELF / status=0`。只做模块枚举的第一次 attach 已完成；第二次 attach 在脚本加载前报进程不存在，所以 Lua 探针和 scheduler hook 均未执行。详情见 [09](09_实机接入尝试与退出记录.md)。

### 2. 不依赖符号名，先从 libc 指针回溯

分析输入为 `recovered/runtime/` 的 PID 12854 快照，读取前校验各段 SHA-256。`scripts/scan_exit_paths.py` 从保存的 maps 求 libc 基址，再用本地 libc 符号找到目标库中的函数指针及 PLT 调用。

在 Cocos 库中定位到：

| 对象 | RVA | 结果 |
|---|---|---|
| libc `exit` 指针槽 | `0xf0fb38` | PLT 在 `0x3b1b50`，扫描到 14 个直接分支调用点 |
| libc `kill` 指针槽 | `0xf10600` | PLT 在 `0x3b30e0`，两个调用点参数分别含 SIGTERM/SIGKILL |
| libc `syscall` 指针槽 | `0xf0fad0` | 三个直接调用点传入系统调用号 98，即 futex；不能误判为退出检测 |

大量 `exit` 调用前显式传入 1 或 -1，不能仅凭存在 `exit` 推断与本次 status=0 有关。Lua `os.exit` 类似入口允许传入状态码，Java 退出对话框也存在 `System.exit(0)`，故还存在其他来源。

### 3. 找到绕开 libc `exit` 的壳内分支

两个库的壳尾部有同构代码：

| 对象 | Cocos RVA | FairGuard RVA |
|---|---|---|
| 状态判断函数起点 | `0xf67510` | `0x4ab510` |
| 状态比较后的条件分支 | `0xf67540` | `0x4ab540` |
| 设置退出码 0 | `0xf6757c` | `0x4ab57c` |
| 调用直接系统调用包装 | `0xf67584` | `0x4ab584` |
| `mov x8, #94; svc #0` | `0xf7a700` | `0x4be700` |

按反汇编可写成下列示意逻辑（对象名称为分析命名）：

```text
context = *(*global_slot)
state = *(context + 0x40)
if uint32(state + 0x430) == 0x79bace2b:
    exit_group(0)
else if uint32(state + 0x430) == 0x4faf2aeb:
    uint16(state + 0x42e) += 1
call_indirect_original(...)
```

这里是 ARM64 Linux 系统调用号 94，具有终止进程所有线程的语义。只拦截 libc `exit()` 无法覆盖这条路径。

进一步在 FairGuard 找到相同常量的生产分支：

- `0x3459c0` 读取某上下文 `+0xaa0` 的 64 位字段；`0x3459c4` 检查 bit 58。
- bit 58 为 1 时跳至 `0x348c38`，构造 `0x79bace2b`，再回到 `0x3459d0`。
- 否则构造 `0x4faf2aeb`；两路在 `0x3459d8` 写入 `x0+0x30`，此前 `x0=state+0x400`。

**证据边界**：生产分支的常量及字段布局吻合消费分支；尚未证明二者在本次现场指向同一个对象。bit 58 可能属于保护策略或状态，尚未还原其上游来源，不能直接命名为“Frida 检测位”。没有本次退出的 PC／调用栈，也没有执行这些代码来验证。

本轮没有修改条件分支、状态字或退出函数。批量屏蔽退出会掩盖其他错误，不能据此认定接入已经稳定。

### 4. 检索局限

两个重建映像中没有找到明确的 `frida`、`gum-js`、`TracerPid` 明文检测字符串；“Friday”是误匹配。缺少字符串不代表没有检测，保护代码仍存在动态字符串、间接调用和混淆。

扫描器覆盖保存映射中的对齐指令候选、标准 PLT 和相邻 ADRP/LDR；不覆盖所有间接调用、匿名映射及未保存的堆。数据区也可能出现指令形状，`svc_candidates` 不是检测函数数量。

## 二、替代脚本入口

### 1. 推荐候选：现有热更新加载链

APK 恢复的 `main.luac`：

- 第 3–5 行先设置初始 `src/res` 路径并加载启动配置。
- `main()` 中重新设置路径，优先加入可写目录 `assets/res`、`assets/src`，之后才加入包内 `res/src`。
- 体验服还会优先加入 `tryver/assets/...`；测试时必须记录实际路径，不能固定假定正式服目录总是获选。
- 接着 `require("sdk_function")`、`require("file_update")`。

热更新 `file_update.luac`：

- `update_finish()` 第 1068 行起清空 `package.loaded` 并 purge FileUtils 缓存，再依次加载配置和业务模块。
- `initInstance()` 的完成回调第 1153 行执行 `require("game_start")`，成功后调用 `beginGame()`。

所以 `game_start` 是更新完成后的候选切入点，能避免过早加载的扩展被更新流程清掉。但只是把新文件放入目录，不会让一个已运行的进程自动执行它；需要后续正常启动／确实触发重新加载，并防止更新覆盖。

**为什么不直接换 main**：原生启动顺序与初始搜索路径早于可写热更新路径生效，两个版本的 main 也不相同。文件存在不等于启动会执行它。

### 2. 原生解码器允许明文：离线验证通过

资源解码入口 Cocos RVA `0x73ca9c` 依次调用两层头部检查，检查函数在 `0x73c808`。只有匹配加密签名时才进入解密包装 `0x4c3fc8`；不匹配时可保留原指针和长度。

新增 `scripts/check_plaintext_decoder.py`：在 Unicorn 中运行保存的原生机器码，构造启用签名检查的资源对象；只允许执行上述解码函数范围，禁止外部函数和系统调用。三份 8／65／288 字节普通 Lua，以及 15,384 字节的暂存探针版本，均满足：

- 返回指针、长度、内容完全不变；
- 没有进入解密包装；
- 没有连接手机，也没有执行 Lua 业务代码。

这证明了**资源解码这一层**的明文直通行为。它不证明 Cocos 的 `require` 会选中指定 `.luac`，也不证明不存在文件校验。旧快照上的字节行为不能代替当前版本实机验收。

### 3. 其他入口的排除／限制

| 候选 | 本轮发现 | 结论 |
|---|---|---|
| `debug_init` / `debug_control` | 手机缓存含这些文件，main 的入口限平台值 0；调试器进一步限 Windows | 不能作为 Android 已开放命令入口；APK main 也没有这段调试初始化 |
| Poco | 热更新 game_start 有 `POCO_ENABLED` 条件和 `poco.poco_manager` 引用 | 尚未证明开关和依赖可用；APK ZIP 未找到字面 `assets/res/poco/` 条目，资源可能另有映射，不能据此宣布可用或完全不存在 |
| `GameHelper.nativeCallLuaFunc` | JNI 回调入口确实存在 | 仍需获得进程内调用能力；不是可直接通过 ADB 调用的导出接口 |
| `Cocos2dxLuaJavaBridge.callLuaGlobalFunctionWithString` | 能调用全局 Lua 函数，前轮已定位内部 RVA | 同样不能消除注入前提；调用 loadstring 仅编译、不等于执行 |
| `web_func.txt` | 下载完成后读文件并 `loadstring` 执行 | 受服务端插更下载流程控制，本地文件会被覆盖，不采用竞态或远程配置修改方案 |

## 三、已准备的最小验证件

- `modules/loader_probe.lua`：只写可写目录的 `dldl_loader_probe.txt`，包含探针版本、时间和 `game_start.luac` 的解析路径；不读取账号信息、不发业务协议、不安装 hook。
- `recovered/phase5/staging/game_start.luac`：完整保留已解密热更新 game_start，末尾追加探针，**仅在本机暂存，未部署**。
- `evidence/phase5_loader_staging.json`：原密文、明文、探针和暂存文件的 SHA-256 及语法检查结果。
- 当前原密文副本：`recovered/phase2/hotupdate/raw/game_start.luac`，SHA-256 为 `033b45a3d279ef2302003ba6f7ec9a6e740f200d9d8c5b775336307d65c35d7f`。后续操作前必须重新读取手机现有文件并比较；旧副本不保证仍是最新版本。

下一次实机验证应按以下顺序执行：

1. 确认可进行一次正常重启验证；记录当前版本、有效路径、原文件哈希、权限和备份。避免运行中修改当前缓存文件。
2. 在实际会被读取的热更新路径部署仅含标记探针的候选文件。若实时文件与暂存基线不符，先重新取出解密，不能覆盖较新的业务脚本。
3. 正常启动，检查是否出现新标记、路径是否符合预期、是否进入游戏及保持稳定。没有标记时先排查寻址、缓存和更新覆盖，不能以“没报错”视为成功。
4. 验证结束恢复原文件，删除探针标记，核对恢复后的哈希。实际恢复若遇新更新，保留新版本，不拿旧备份覆盖。
5. 只有这条通道稳定后，再把自定义模块安装器接到相同位置，并做香香小助手 UI 与协议回执验证。

本轮用户要求先定位，因此当前进程保持运行，没有开始上述部署或重启。

## 四、对最终功能的影响

资源解密与业务定位没有倒退；阻塞点是稳定加载方式。推荐先走游戏自己的热更新通道，把壳内退出状态的上游分析作为备用路线。

正确的两项免费领取仍是斗罗集市每日礼包、学院活动每日特惠，不是修炼补给。两项礼包执行器尚未实现；乾坤问情谷扫荡、镜之屋每日免费召唤、众神殿膜拜也未实机部署。本轮探针没有执行任何这些操作。
