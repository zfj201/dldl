## 后续优先级 1：拿到真实解密输出

已准备 `scripts/capture_xxtea.js` 和 `scripts/capture_xxtea.py`，**未动态执行／验证**。

选择 `cocos+0x4c3b60` 的理由：它是标准 XXTEA core，运行时 FairGuard 在 wrapper 前先处理输入；core 返回的成功结果最适合验证离线恢复。只 hook wrapper 入参会拿到额外保护尚未消除的密文。

Frida 脚本：

- 检查 ARM64、库名、函数序言和样本常量后再 attach。
- 在 core 入口保留 `args[3]` 的输出长度指针，返回时读取 `retval` 指向的数据。
- 不修改参数、返回值，不主动调用游戏函数，不重启游戏。
- 最多捕获 256 个缓冲区／256 MiB，单个不超过 32 MiB，按 SHA-256 保存。

依赖前提：电脑安装 Frida Python 包，设备端有兼容且正在运行的 Frida server。本轮只有设备端文件存在证据，没有启动服务。技能里关于 Frida 已安装的描述与当前 PATH 实测不一致，应以实测为准。

准备好环境后才执行：

```sh
python3 scripts/capture_xxtea.py --device '<frida设备ID>' --pid '<当前游戏PID>' --seconds 30
```

这条命令为下一阶段方案，不是本轮成功执行记录。attach 后只能捕获新发生的资源读取；进程启动时已经加载的脚本不会自动重新出现。需要在测试场景触发对应资源加载，或另行设计早期加载采集。若 FairGuard 拒绝 attach，应保留错误，转下面的离线方案；不能把空输出认作客户端没有 Lua。

输出验收：检查 Lua 文本语法、Lua 字节码魔数／版本，或者 PNG、ZIP、CCZ、FMOD 等正确文件结构。第一次 XXTEA 输出仍可能是下一层带签名容器，需要继续按已确认链路处理。运行时输出还要核对是 APK 内资源还是热更新内容。

## 后续优先级 2：离线还原资源预处理

从已采集 `libFairGuard.so` 的 RVA `0x341660` 继续：

1. 完整界定前置函数和被调用函数，追踪全局状态、密钥表和受影响字节范围。
2. 选择小资源，记录同一 buffer 在预处理前／后的变化，作为独立测试样本。
3. 实现本地预处理，再接标准 XXTEA，要求输出与运行时字节逐一相同。
4. 分别验证短文件、超过 4096 字节文件、bootstrap 和图片，避免把单一样本成功推广到全部资源。
5. 成功后遍历 APK 资源，生成 `输入路径 -> 输出哈希 -> 格式 -> 校验结果` 清单，对失败条目保留原因。

本轮不输出猜测性的批量“解密成功”文件。`probe_xxtea.py` 只是明确记录基础算法直解失败的验证脚本。

## 后续优先级 3：恢复脚本与逻辑目录

- 先还原 bootstrap 与 `main.lua` 依赖树，寻找路径哈希映射和热更新版本信息。

- 将战斗、角色成长、UI、网络协议、资源管理等模块分别标注“实际有源码／只有字节码／仅 native／服务端缺失”。
- 用具体行为验证少量代表性模块，再评估整体覆盖率。APK 内文件数不能代表逻辑覆盖率。
