# 斗罗集市每日礼包、学院活动每日特惠定位

日期：2026-10-11。用户纠正：“每日签到”实际指 **斗罗集市→每日礼包** 和 **学院活动→每日特惠** 的免费领取，不是修炼补给。

**定位已完成：两项共用 VipController 的礼包查询／免费领取接口，可作为两个独立本地任务接入香香小助手。此轮仅定位，没有执行领取、编写新领取执行器或修改手机。** 原 `daily_sign.lua` 与 `xiangxiang_sign_extension.lua` 实现的是修炼补给，不满足此需求，保留为历史技术验证，不能作为本目标已完成的证据。

## 两项目标

| 内容 | 斗罗集市→每日礼包 | 学院活动→每日特惠 |
|---|---|---|
| 页面 | `MonthWeekPanel` | `EveryDayGiftPanel` |
| 本地页签索引 | `VipConst.VipTabConst.DayGift=101` | `176`，`WelfareIcon.every_day_gift=10006` |
| 查询 | `VipController:sender21017(1)` | `VipController:sender21017(6)` |
| 免费项 | 当前配置 `charge_id=9991` | `VipModel:getCurDailyData()` 选出的 `purchase_free`；当前配置 `9995` |
| 领取 | `VipController:sender21018(charge_id)` | 同左 |
| 可领条件 | 服务端本次 gift_type=1 列表含免费项，且 `buy_count < limit_count` | 服务端本次 gift_type=6 列表含对应项，`checkFreeDailyGift(id)` 为真，且 `buy_count < limit_count` |
| 查询完成事件 | `VipEvent.Updata_Week_Month_Data(index)`，仅接受 index=101 | `VipEvent.Update_Every_Day_Gift` |
| 数据读取 | `VipModel:getMonthWeekData(101)` | `VipModel:getMonthWeekData(176)` |

当前 `ChargeLoopData.data_award_name` 中 9991 与 9995 均为 `is_free=1, limit_count=1, buy_charge_id=0`。这描述本地配置，不证明账号当前一定可领取。礼包未出现在服务器列表时应跳过，不能用配置代替账号状态。

## 免费选择与付费分支

斗罗集市：`MonthWeekItem` 只在 `last_count>0` 时调用面板回调；`MonthWeekPanel:itemCallback` 对 `charge_id>9990` 调用免费领取接口。自动任务应进一步限定 gift_type=1 和对应免费配置，避免把整页所有商品或其他免费礼包都算入任务。

每日特惠：`VipModel:getCurDailyData()` 按 `TimeTool.checkServerOpenTime` 选择 `ChargeLoopData.data_daily_deal`，返回付费组合、组合购买 ID、免费 ID；`checkFreeDailyGift(id)` 比较第三个值。当前条目 `purchase_free=9995`，付费商品为 481/482/483，组合购买为 484。不要将 gift_type=6 套成 `9990+6=9996`，9996 在配置中属于另一类新手礼包。

实现时复用原模型的配置选择，并核对服务器列表及 `is_free`。不调用 `sdkOnPay`、一键购买或代金券购买入口。

## 真实协议与完成判据

热更新 `sys/net/proto_mate.luac` 已恢复：

- 请求 `21017`：`gift_type:uint8`。
- 返回 `21017`：`reg_day`，`gift_loop_list[]`，每组含 `gift_type/ref_time/gift_list[]`；商品含 `charge_id/limit_count/buy_count/rewards` 等字段。
- 请求 `21018`：`charge_id:uint32`。
- 返回 `21018`：只有 `code:uint8,msg:string`，**没有 charge_id、gift_type 或领取后的计数**。

`VipController:handle21018` 是空函数，不能依赖它现有的成功事件。`handle21017` 更新模型，计算 `last_count=max(limit_count-buy_count,0)`，再发对应页签事件。

建议接入状态流：

```text
查询指定 gift_type
  → 匹配免费 ID 和剩余次数
  → 已领／未开放则跳过
  → 领取一次，等待 21018
  → 查询同一个 gift_type
  → 同 charge_id、同 ref_time 的 buy_count 增加，确认本次领取
```

两个任务必须串行，并避免与手动领取并发，因为 21018 没有商品关联字段。成功码只作为触发核实的依据；查询后的实际计数才是完成依据。查询事件也会由其他页面或服务器推送触发，需要匹配组、商品与周期。

失败回执或超时后查询状态，不直接重发。若 `ref_time` 已切换，应作为跨周期不确定结果处理；不能把新周期数据当成上次领取成功。服务器是否主动推送 21017、回执具体时序、真实奖励到账尚待实机验证。

## 后续模块调整

1. 斗罗集市·每日免费礼包。
2. 学院活动·每日特惠免费领取。

原来的 14100/14101 状态机需要替换为 21017/21018 的礼包状态机，不能只改标题。之前验证过的小助手本地注册、服务器任务编号过滤、队列分流和卸载思路可以复用；旧 15 项测试不能证明新目标正确。
