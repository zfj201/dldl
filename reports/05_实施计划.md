# 内置香香小助手扩展实施计划

> 2026-10-11 目标修正：每日签到实际为“斗罗集市→每日礼包”和“学院活动→每日特惠”免费领取。旧修炼补给原型不满足此需求；两项新目标已定位，详见 [最新定位报告](08_每日礼包与每日特惠定位.md)。

> 阶段更新：已恢复可读 Lua 并完成签到离线原型，详见 [06 资源解密记录](06_资源解密与业务恢复.md) 与 [07 模块实现记录](07_模块定位与签到原型.md)。下文保留该阶段的判断／计划，不代表最新完成状态。

用户确认：扫荡特指 **乾坤问情谷扫荡**。目标是在游戏内置香香小助手增加四个可选任务：每日签到、乾坤问情谷扫荡、镜之屋每日召唤、众神殿自动膜拜。

目前仍处于入口定位阶段；以下为计划与验收标准，不是完成记录。

## 1. 取得目标 Lua 代码

优先验证已准备的解密输出采集方案：检查 Frida 客户端／设备端兼容性，确认目标进程与 APK 版本，再验证能否捕获 XXTEA core 的有效返回缓冲区。已有 Hook 脚本仅通过语法检查，尚未动态验证。

结合解密出口与必要的 Lua 加载边界，记录缓冲区内容、调用来源、脚本名或 chunk 名与哈希。不能假设 XXTEA 的每个输出都是 Lua；必须先辨认源码、字节码、压缩数据或中间层密文。

围绕小助手和四项玩法的页面加载收集代码。如果脚本启动时已缓存，仅打开页面可能不会再次触发解密，需要根据实测选择启动期采集或已加载模块定位。

验收：得到至少一个可确认属于小助手或目标玩法的客户端脚本／字节码，并能把它与实际界面对应。不能以资源图片名、字符串命中或导出 MB 数代替此验收。

若动态采集不可用，转向已定位的 FairGuard 前置函数做离线恢复；保留具体失败证据，不扩散到无关 SDK 逆向。

## 2. 弄清小助手如何注册和执行任务

恢复并画出以下调用关系：

```text
小助手页面
  -> 任务列表来源 / 任务注册
  -> 勾选项与配置保存
  -> 开始执行与队列调度
  -> 单项任务入口
  -> 回执处理与任务完成标记
```

重点区分客户端逐项执行和服务器固定一键任务。如果是后者，核实是否能在客户端追加本地任务并调用游戏已有的单项操作；不能凭空添加服务器任务编号。

验收：解释一个已有助手任务从界面到完成的完整路径，确定新增项需要修改的最少位置。此时才能决定是 Lua 注册项扩展、客户端调度扩展，还是当前版本无法直接接入。

## 3. 每日签到做第一个可运行样例

恢复可领取判断、正常领取入口和状态更新回调，接入新增的“每日签到”开关。先复用游戏已有调用，不猜测协议号或参数。

验收：新选项可显示；执行后以真实状态确认成功；已签到则跳过；重复启动助手不重复提交；网络超时先核对状态再重试。

## 4. 接入其余三个模块

| 模块 | 需要核实 | 完成判据 |
|---|---|---|
| 镜之屋每日召唤 | 对应池／类别、免费次数或冷却、真实消耗参数 | 免费召唤成功并更新次数；免费机会耗尽时跳过 |
| 众神殿自动膜拜 | 功能资格、可膜拜对象、普通／高级档位及消耗 | 正常回执与剩余次数一致；不重复膜拜 |
| 乾坤问情谷扫荡 | 功能开放与可扫荡条件、实际目标／层数参数、次数上限、实际消耗 | 正常扫荡回执与次数／奖励状态一致；无资格或次数不足时跳过 |

以上参数类型是待检查项，不宣称该玩法必然存在所有字段。尤其乾坤问情谷不能套用其他副本的体力、层数或关卡模型。

三个模块复用已验证的执行、等待回执、完成、跳过、异常处理约定，逐个加入助手队列，避免并发干扰。

## 5. 验证可重复加载与交付方式

开发验证可先使用受控的运行时扩展，但最终交付需要确定实际加载入口，验证重启、重新登录、切换角色以及热更新后的行为。如果必须修改资源／APK，需要单独验证签名、完整性和启动兼容性。

验收：四个任务能够在香香小助手中配置和执行；重启后能按设计重新加载；版本不匹配时给出明确错误；保留可撤销的变更及说明。不会把一次性内存 Hook 成功描述为已经完成可长期使用的模块。

## 每阶段交付

- 代码恢复阶段：目标脚本／字节码、哈希、来源与覆盖清单。
- 任务分析阶段：真实注册项、调用链、必要修改点与未解决问题。
- 单模块验证阶段：实现、运行日志、状态前后对照及失败处理。
- 最终集成阶段：四项任务、加载方案、版本适用范围和更新后的验证记录。

下一项最有价值的工作是：验证解密采集，取得小助手和签到的实际 Lua 代码，并判断客户端能否扩展任务队列。
