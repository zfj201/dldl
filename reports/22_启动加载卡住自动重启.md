# 启动加载卡住自动重启

日期：2026-10-24；模块版本：0.4.1。

## 请求与定位

用户截图为黑底“健康游戏忠告”上叠加“正在加载中...”进度框。已恢复的 Java 源码确认其来自 `com.sqwan.msdk.api.sdk.Huawei.showLoading()`：创建原生 `android.app.ProgressDialog`，在 `JosAppsClient.init()` 异步回调中通过 `hideLoading()` 关闭。此时不一定具备可用的游戏 Lua 或主城状态，恢复不能依赖 GL 线程和 Lua 心跳。

## 已实现

- LSPosed 只监听该 SDK 类的 `showLoading()` / `hideLoading()`，不全局拦截进度框，也不使用截图模板。
- `SdkLoadingMonitor` 在主线程观察实际 Dialog 是否显示、窗口是否可见且拥有焦点，每500毫秒写入私有 `sdk-loading.tsv`。失去焦点、关闭、切换请求或实例都会重新计时；重复show同一可见实例不重置计时。
- 配置应用的前台服务使用 `elapsedRealtime` 计时。连续显示**超过15000毫秒**后，经Root检查游戏PID、当前窗口、加载状态、启动进度、撤销标记及助手请求，确认仍处于启动加载阶段才 `am force-stop` 并重新启动游戏。检查约每秒执行，Root操作耗时可能使实际触发稍晚于15秒。
- 即使游戏主线程停止采样，外部服务仍按最后的可见状态计时；杀进程前会检查当前焦点及私有状态。若已隐藏、切到后台、PID变化或登录进度推进，则跳过。
- 每次自动启动最多重启3次，第4次持续卡住时报告 `blocked / sdk_loading_retry_exhausted`，撤销请求并退出服务。重启保持原请求ID、角色及300秒有效期，不清消费journal。
- 一旦进入开始冒险、主城或助手执行阶段，关闭本次加载恢复监控，并恢复原来的业务回执轮询频率，避免执行助手期间额外高频Root操作。
- 只作用于每天07:00、立即运行和仅验证启动。没有有效启动指令的普通手动打开游戏不触发这项恢复或自动任务。

关键实现：`LoadingRecovery.java`、`SdkLoadingMonitor.java`、`DldlModule.java`、`AutomationService.java`、`RootAccess.java`。APK、Lua引导器和资源清单版本统一为0.4.1。

新增测试覆盖15秒边界、隐藏/重新计时、游戏主线程冻结后的外部计时、请求与PID格式、单调时钟、启动阶段隔离及3次重启上限。既有加载器111项回归通过；Lint无错误，保留原有8项警告。

真机验证使用同一 Redmi Note 12T Pro / Android15，仅执行 `verify`，没有发完整助手请求：

1. 真实SDK加载框正常关闭，状态文件为hidden，没有误触发恢复。SDK Hook已就位，正常启动最终返回 `verified / city_and_role_ready`。期间出现另一类华为活动推广，需要手动逐个关闭；本次加载超时恢复不会把这些广告当作该加载框，也未新增该广告入口的拦截。
2. 受控协议测试：先让真实加载框退出，再向私有状态协议写入“已连续可见超过15秒”的模拟记录。游戏在后台时记录 `not_foreground`，PID不变；回到前台后由模块实际执行杀进程及重启，PID改变，日志记录首次 `restarted`。
3. 重启前后launch完全一致，保留请求ID、有效期和verify模式；没有生成对应的助手业务请求。该测试验证服务与Root恢复链路，**不等同于自然复现SDK真实卡死**。
4. 验证结束撤销请求、关闭测试游戏，确认launch已清理、前台服务退出；原每天07:00精确闹钟保留，系统下一次预约为2026-10-25 07:00。

私有证据位于已忽略的 `evidence/phase15/loading-recovery-device.json`、`loading-recovery-cleanup.txt` 和相应截图，不提交角色信息或诊断工具。临时Root Frida服务的启动被自动审核拒绝，因其开放设备级进程注入能力；本次改用上述私有协议测试，未启动该服务，也未通过其他方式注入游戏进程。
