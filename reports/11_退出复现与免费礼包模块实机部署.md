## 一、退出原因：受控测试与证据边界

| 对照／实验 | 条件 | 结果 |
|---|---|---|
| PID 12496 基线 | 未运行 Frida 服务，未附加 | 约 21 分钟持续存活；无新增退出记录 |
| 版本核对 | Python Frida 与手机 frida-server | 均为 17.18.0，排除明显版本不一致 |
| 最小 Frida 附加 | 启动已有服务，对 12496 attach；计划只发就绪标记，无 Hook、无 Lua | `01:57:51.012` 开始 attach，`01:57:52.421` 返回 ProcessNotFoundError；系统 `01:57:52.985` 记录 EXIT_SELF/0。未到脚本加载阶段 |
| 仅服务存在 | 服务仍运行，正常启动 PID 21705，不 attach | 能停留在版本提示并进入登录页，观察至 02:00:28 仍存活 |

**判断：反调试／动态接入相关的主动退出是目前最有力解释，不能继续当作一次普通偶发闪退处理。** 最小附加复现与前次 8136 的行为一致；strace 也触发同类退出，说明嫌疑不限于 Frida JS 或礼包代码。

但还不能严格宣布“已证明某个 Frida 专用检测函数”：样本次数有限，strace 在进入账号时执行，存在时序扰动；未取得原次 PID 8136 的调用栈，也未完全排除注入兼容性或其他接入相关问题。仅服务存在的对照停留在启动／登录阶段，不能外推所有主城场景均不检测服务。

### 捕获到的退出现场

`logs/phase6_strace_control.txt`：

```text
[pid 21727] 02:01:00.459903 [0000007f00e76008] exit_group(0 <unfinished ...>
```

其他 PID 232xx 是 `-f` 跟到的派生进程，不应把其 exit_group 当作目标游戏退出。前面还有 SIGSEGV 信号记录；Android 运行时可能处理此类信号，它们不是本次已确认的致命崩溃证据。最终系统记录是 EXIT_SELF/0。

退出 PC 不在上一轮定位到的两个壳内 exit_group 包装地址附近。旧 PID 19372 的 maps 中相同虚拟地址曾对应已删除 ashmem 页，但地址可在不同进程复用，**不能用旧映射给 PID 21705 的现场归属定案**。本次没有同时保存该进程在退出瞬间的映射／调用栈，因此尚未确认实际检测函数。

### 对上一轮“状态字”的修正

`phase6_guard_before.json` 的只读链式读取显示，两个库的 `context+0x40` 均指向各自模块基址。上一轮示意的 `state+0x430` 在此现场其实是映像内的字段，读值分别为 `0x5a`、`0x40`，不是 `0x79bace2b`。

所以它不能直接称为“当前 Frida 检测状态位”。上一轮的机器码分支与常量生产代码仍然存在，但没有证据证明上次或本次退出经过那条分支。本轮没有据此盲目写状态位或屏蔽退出。

## 二、“反反 Frida”评估与路线选择

- **仅改服务名字／端口**：本轮仅服务运行并没有立即退出，attach 和 strace 才出现可复现的关联。简单改名没有足够证据支持，不能视作已验证解决方案。
- **注入后 Hook exit／ptrace**：最小附加已在脚本加载前失败，此时依赖注入后 Hook 的方案可能太晚；此外 native 直接 syscall 不一定经过 libc 导出。
- **提前定点修改检测分支**：需要证明实际检测点及原始字节，建立可恢复方案。上一轮候选尚未与现场连上，不能盲目 patch。
- **无需附加的脚本入口**：本轮已经成功验证，能完成用户要求的模块显示。因此按用户设定的备用路线部署，没有继续无边界试错或宣称已实现通用反反 Frida。

02:17:41 最终核对：PID 28634 仍在运行，距模块部署约 10 分钟，安装哈希不变；Frida 服务未运行。

本轮结束时 Frida 服务已停止。使用热更新绕开“附加过程”，不等于已经破解全部保护。

## 四、两个模块的实现

| 项目 | 行为 |
|---|---|
| 斗罗集市每日礼包 | 查询 21017(gift_type=1)，仅选择免费 ID 9991 |
| 学院活动每日特惠 | 查询 21017(gift_type=6)，使用原 VipModel 返回的 purchase_free，当前为 9995 |
| 免费校验 | 配置必须 is_free=1、gift_type 匹配、buy_charge_id=0，且服务端列表确实包含该项 |
| 剩余次数 | 服务端 buy_count < limit_count 才允许提交 |
| 领取 | 仅复用 sender21018；不调用付费 SDK／代金券购买 |
| 成功判据 | 21018 后重新查询，同礼包、同 ref_time，buy_count 增加才算已核实 |
| 超时／失败 | 再查询状态，不自动重发领取；未确认则停止当前队列 |
| 并发 | 两项共用串行状态机；执行期间拦住同控制器的手动免费领取，新任务也会避开已发出的手动请求窗口 |
| 账号切换 | 检测角色身份变化并取消，避免继续操作旧角色 |
| 自定义编号 | 使用本地负编号；保存时从 31601 过滤，31602 另加断言防误发 |
| 开关 | 默认关闭；用户保存后，按区服／角色写入本地偏好，不向服务器存储自定义编号 |
| 卸载 | 关闭助手窗口后可恢复包装的方法并移除本地条目；重启恢复原 game_start 则不再安装扩展 |

协议分发器 `ProtoMgr:RegisterCmdCallback` 的闭包在收到数据时动态查 `obj[func_name]`，因此包装现有 VipController 方法可实际被已注册的回调使用；离线测试使用恢复出的真实分发器验证过该机制。
